# Дизайн-система для curehht.github.io

## Why

Публичный сайт должен оставаться читаемым и доступным для пациентов на телефоне, при увеличении текста и при работе с клавиатурой. Администратору нужны значительно более сложные формы и элементы управления. Сейчас простые элементы управления реализованы в проекте вручную, а общий язык цветов, размеров, состояний ошибок и русских текстов не задан.

Исследование выполнено 27 октября 2026 года по состоянию этого worktree (`package.json`: Next.js `^16.1.6`, React `^19.2.4`, TypeScript `^5.9.3`). В нём **нет** `AGENTS.md`, `docs/specs/` и `docs/changes/_template.md`; поэтому использованы требуемые разделы шаблона из задачи. Действующее правило UI находится в `.cursor/rules/common.mdc` и говорит «Do not use any UI frameworks or library». Оно противоречит предлагаемому решению и потребует отдельного согласованного изменения при внедрении. Здесь меняется только этот документ.

## What changes

**Рекомендация: Mantine 9 для `/admin`, собственные семантические HTML-компоненты и CSS Modules для публичных маршрутов.** Это один разделённый по маршрутам дизайн-контракт: общие CSS-переменные цветов, типографики, отступов и состояний; Mantine применяет их только в админке. `Document`, навигация, новости и подвал продолжают рендериться сервером без MantineProvider. Mantine выбран за готовые формы и совместимость с текущим способом стилизации. Его документация прямо говорит, что все компоненты Mantine являются Client Components, поэтому применять их к публичному тексту нельзя без роста JS. [Mantine Next.js](https://mantine.dev/guides/next/), [CSS Modules](https://mantine.dev/styles/css-modules/).

Цена решения: две реализации простейших визуальных элементов (публичная HTML/CSS и административная Mantine), клиентский код Mantine в админке, отсутствие встроенной сортировки блоков и полноценной таблицы данных с серверными запросами. Это приемлемо, поскольку публичный рендеринг и админские сценарии имеют разные требования. `@mantine/form` — локальный механизм состояния формы, не глобальная библиотека состояния приложения.

## Requirements

- **SHALL** сохранять публичные страницы, документные блоки, новости, навигацию и подвал серверными компонентами там, где не нужна интерактивность; интерактивные островки **SHALL** быть локальными.
- **SHALL** подключать MantineProvider, стили Mantine, провайдер дат и уведомления только в административном layout или его клиентском поддереве; публичный layout **SHALL NOT** импортировать административные компоненты, провайдеры и их общий barrel.
- **SHALL** обеспечивать корректный статический экспорт только публичных маршрутов. Авторизация, cookies, redirects, запросозависимые API и Server Actions **SHALL NOT** попадать в дерево маршрутов экспортируемой сборки. Отдельный маршрут сборки — архитектурная предпосылка, а не функция UI-библиотеки. [Next.js static exports](https://nextjs.org/docs/app/guides/static-exports).
- **SHALL** задавать фиксированную локаль `ru-RU` для интерфейса и дат, явные русские подписи, ошибки, действия и сообщения; формат дат **SHALL** быть одинаковым при серверном рендеринге и гидратации.
- **SHALL** использовать CSS Modules и общие CSS-переменные для видимой согласованности; тема админки **SHALL** задаваться через `createTheme`/MantineProvider и документированные `classNames`/Styles API.
- **SHALL** проверять WCAG 2.2 AA: контраст обычного текста не ниже 4.5:1, крупного не ниже 3:1, читаемость при увеличении текста до 200%, видимый фокус, управление клавиатурой, доступные имена полей и сообщения об ошибках. Для пациентов проект **SHALL** выбирать комфортный базовый размер и длину строки, а не минимально допустимые значения. [WCAG 2.2](https://www.w3.org/TR/WCAG22/).
- **SHALL** измерять, а не предполагать, объём JS/CSS публичных страниц до и после внедрения; административный UI **SHALL** оставаться за границей `/admin`.
- **SHALL** сохранять TypeScript-типы данных и узкие свойства проектных обёрток; добавляемые компоненты **SHALL** иметь небольшой пример использования с русской подписью, ошибкой, disabled/loading и фокусом.

## Approach

Такое утверждение нельзя вывести только из поддержки Next.js App Router: экспорт ограничен маршрутизацией и серверными возможностями Next.js. Указания «App Router/React» ниже относятся к официальным руководствам; где нет прямого упоминания Next.js 16 или React 19, это отмечено. Оценка размера bundle — качественный вывод из наличия клиентского runtime, CSS и возможности импорта по маршрутам; проверенных цифр для этой сборки нет.

### Оценки

Шкала 1–5: 5 лучше. «RSC/экспорт» оценивает архитектурную пригодность при изоляции админки, а не обещание официальной поддержки static export. «Публичный bundle» — ожидаемая простота удержания JS/CSS вне публичных маршрутов, без выдуманных KB. Вес критериев одинаковый; итог помогает сравнить, но не заменяет учёт уже существующей CSS Modules архитектуры.

Mantine получает преимущество именно в этом репозитории: покрывает почти все запрошенные административные контролы и использует CSS Modules. React Aria ближе по сумме, имеет более глубокую поддержку доступного drag-and-drop, но потребует вручную построить и поддерживать гораздо больше админских поверхностей. Ant Design богаче в таблицах/загрузке и имеет готовую русскую локаль, зато потребует управлять CSS-in-JS/registry и App Router-ограничениями. Числа a11y не означают автоматического соответствия WCAG: это оценка примитивов и документированных практик.

### План внедрения (после принятия решения; сейчас ничего не устанавливается)

1. **Граница сборок.** Зафиксировать публичный-only export target, который не включает `/admin`, `/api/auth`, `/api/upload` и связанные динамические маршруты. `next.config.js` включает `output: 'export'` по `NEXT_EXPORT_TYPE`, но в текущем дереве также есть `auth()`/`redirect()` в `src/app/admin/layout.tsx` и API routes. Документация Next.js исключает cookies, redirects, request-dependent handlers и Server Actions из static export; успешность имеющейся экспортной сборки не проверялась. Если она падает, понадобится отдельное дерево/приложение сборки для публичных страниц; скрыть ссылки недостаточно.
2. **Установка после проверки версий.** Для минимального пилота: `pnpm add @mantine/core@^9 @mantine/hooks@^9 @mantine/form@^9 @mantine/dates@^9 dayjs`; позже по используемым сценариям `pnpm add @mantine/dropzone@^9 @mantine/notifications@^9 @mantine/carousel@^9 embla-carousel@^8 embla-carousel-react@^8`. Держать все `@mantine/*` на одном major и проверить актуальные peer dependencies перед фиксацией версий. [Mantine Next.js setup](https://mantine.dev/guides/next/), [dates](https://mantine.dev/dates/getting-started/), [carousel](https://mantine.dev/x/carousel/).
3. **Тема и локаль.** Ввести проектные CSS-переменные для текстового/фонового/акцентного цвета, границ, фокуса, шрифта и отступов в `src/app/global.css`; выбрать комфортные размеры и проверить светлую/тёмную схему. В клиентском компоненте `AdminProviders` использовать `MantineProvider` с `createTheme`, `DatesProvider settings={{ locale: 'ru', firstDayOfWeek: 1 }}`, импорт `dayjs/locale/ru` в том же клиентском файле и один `Notifications`. CSS Mantine (`@mantine/core/styles.css` и стили дополнений) импортировать только из административной границы, если сборщик это позволяет; проверить фактическое CSS-разделение. Не переносить провайдер в корневой layout. [Mantine Next.js](https://mantine.dev/guides/next/), [ru/SSR note](https://mantine.dev/dates/getting-started/), [CSS import](https://mantine.dev/styles/mantine-styles/).
4. **Пилот миграции.** Сначала `Button`, `Input`, `TextArea`, `Checkbox`, `Radiobox`, `Select` внутри `PageForm` или `RoleForm`: видимые русские label/error/description, валидность, фокус и disabled/loading. Затем `PageForm`/`DocumentForm` и `RoleForm` на `@mantine/form` с сохранением серверной проверки данных. Затем `DocumentDelete`/блочные подтверждения на Modal, ошибки и успехи на Notifications. Потом UsersList/RolesList и загрузка файлов. Таблицу брать из Mantine Table только если хватает требований к сортировке и действиям; иначе оценить отдельное решение без утечки в public.
5. **Специализированные сценарии.** Оставить TinyMCE динамическим в админке. Для сортировки блоков выбрать клавиатурно доступный DnD и хранить порядок как часть доменной модели; текущий HTML drag-and-drop этого не гарантирует. Для файла Mantine Dropzone лишь передаёт `File` в существующий авторизованный обработчик. Carousel/Slider/Tabs/DatePicker подключать только по реальному экрану, не заранее.
6. **Проверка.** Сравнить build trace и JS/CSS публичных страниц до/после, выполнить динамическую и публичную export-сборки, вручную проверить mobile 320px, 200% zoom, клавиатуру/скринридер, русские даты, тёмную тему, диалоги и ошибки. Для гидратации использовать фиксированную локаль и избегать `Math.random()`, browser timezone и browser APIs во время render.

### Риски и вопросы владельцу

- **Граница static export:** какая сегодня команда/CI создаёт публичный GitHub Pages артефакт и действительно ли она исключает динамические маршруты? Нужна проверка до миграции UI.
- **Бренд и доступность:** есть ли утверждённые цвета, шрифт, режим высокой контрастности и пользовательские требования к 200%/400% увеличению? Предлагаемые токены требуют проверки на реальном русском контенте.
- **Админские таблицы:** достаточно ли простых списков/таблиц, или нужны большие наборы с серверной сортировкой, фильтрацией и виртуализацией? Mantine Table не решает это целиком.
- **Блоки:** нужна ли сортировка на сенсорном экране и с клавиатуры, и требуется ли атомарное сохранение нового порядка? Существующий DnD сохраняет позиции по одному блоку.
- **Редактор и файлы:** остаётся ли TinyMCE, как обрабатываются изображения, ограничения загрузки и русская локализация его плагинов?
- **Лицензии и обновления:** в Mantine core и перечисленных addons MIT, но при выборе отдельной DnD/data grid/editor-библиотеки проверить её лицензию и версии отдельно.
